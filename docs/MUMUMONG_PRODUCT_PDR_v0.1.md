# MUMUMONG(무무몽) Product Planning + PDR v0.1

범위: 3개월 사이드프로젝트 MVP (1인 개발, iOS 단일 출시, AI 코딩 에이전트 활용)
기준 루프: **꿈 기록 → 꿈 분석 → 기존 원고와 연결 → 소설 생성 → 사용자 디렉팅 → 원고 성장 → 사용자가 완결**

> 기능 추가 판단 규칙: 위 7단계 중 하나를 **더 단순하게** 또는 **더 매력적으로** 만들지 않으면 MVP에 넣지 않는다.

---

## 1. Product Vision

사람은 매일 밤 이야기의 재료를 만들지만, 아침이면 대부분 사라진다. 무무몽은 그 재료를 붙잡아 **출처가 있는 소설**로 쌓고, 사용자가 자기 이름으로 한 권을 완결하게 한다.

장기적으로 무무몽은 "꿈에서 온 책"을 만드는 개인 출판 브랜드가 된다. MVP의 목표는 그 첫 권, 즉 VOL.01을 완결하는 사람이 실제로 존재하는지 확인하는 것이다.

## 2. 한 문장 Product Definition

- **사용자용:** 꿈을 기록할 때마다 나만의 소설이 조금씩 완성되는 창작 앱.
- **내부용:** 실제 꿈을 출처로 가진 소설(Dream-sourced Fiction)을, 사용자가 연결과 방향을 결정하며 완결까지 이끄는 원고 도구.

## 3. Target User / JTBD

**ICP (초기 핵심 사용자)**
- 20~30대, 기록형·수집형 성향이 있는 사람. 다꾸, 필사, 포토북, 독립출판물 구매 같은 습관이 있다.
- 꿈을 가끔 흥미롭게 기억한다. 주 1~3회 수준.
- 글쓰기 자체가 취미는 아니지만 "내 이름이 박힌 결과물"을 갖고 싶어 한다.

**Anti-ICP (의도적으로 배제하는 사용자)**
- 해몽이나 길흉을 원하는 사용자
- 전문 작가, 웹소설 연재자
- 자각몽 훈련자

이들의 요구를 받아들이면 제품이 다른 카테고리로 끌려간다.

## 4. Positioning / Category

- **사용자에게 보이는 카테고리:** "꿈 일기"라는 익숙한 멘탈 모델 위에 "책 만들기"를 얹는다. 짧게는 **"꿈으로 쓰는 책"**이다.
- **신조어는 쓰지 않는다.** Living Novel, Dream Serial 같은 용어는 설명 비용만 늘린다.
- **App Store:** Primary는 **도서**, Secondary는 **라이프스타일**을 권장한다. 꿈 앱들이 몰린 라이프스타일/건강 카테고리를 피해 카테고리 자체로 차별화하는 전략이다. "꿈 일기, 꿈 기록" 검색 유입은 ASO 키워드로 확보한다.

| 대안 | 사용자가 얻는 것 | 무무몽과의 차이 |
|---|---|---|
| 꿈 일기 앱 (해몽·분석) | 기록, 해석, 패턴 | 결과물이 없다. 무무몽은 **책**이 남는다 |
| ChatGPT | 1회성 변환 | 누적, 출처 추적, 완결 구조가 없다 |
| AI 스토리 플랫폼 | 가상 설정 기반 창작 | 재료가 발명된 것이다. 무무몽의 재료는 **실제 경험**이다 |
| 기록→책 서비스 (StoryWorth류) | 기록이 책이 된다 | 가장 가까운 멘탈 모델. 무무몽은 그 **꿈 버전** |

## 5. Core Value Proposition

1. **빈 페이지가 없다.** 기억나는 만큼 말하면 원고가 자란다.
2. **출처가 있는 소설이다.** 모든 장면이 어느 날의 어떤 꿈에서 왔는지 보인다.
3. **끝이 있다.** 사용자가 결정한 시점에 한 권으로 완결된다.

## 6. 핵심 Product Principles

각 원칙에는 반드시 구현 규칙이 따라붙는다. 구현 규칙이 없는 원칙은 슬로건일 뿐이다.

| # | 원칙 | 구현 규칙 |
|---|---|---|
| P1 | 꿈이 출처다 | 모든 문단에 출처 태그를 붙인다. D(꿈), C(연결·각색), U(사용자 작성) |
| P2 | 부풀리지 않는다 | 생성 길이는 재료량(MU, §15)으로 상한을 둔다. 검증기가 강제한다 |
| P3 | 깨어난 순간엔 결정이 없다 | 기록 화면에 선택지 0개. 저장은 1탭 |
| P4 | 의미 있는 선택은 읽을 때 한다 | 연결 결정은 생성 후 리빌 화면에서. 꿈 1개당 최대 1문항 |
| P5 | 각색은 허용 범위 안에서, 보이게 한다 | 각색 수준이 C 문장 예산을 결정한다. C는 항상 표시 가능해야 한다 |
| P6 | 장르는 결과값이다 | 시작 시 장르 선택 없음. 누적 태그로 형성하고 제안만 한다 |
| P7 | 진척은 설명 가능해야 한다 | 모든 증가분에 사유를 표시한다. 사용자가 직접 뺀 경우 외에는 감소하지 않는다 |
| P8 | 사용자 문장은 AI가 덮어쓰지 않는다 | U 문단은 잠금. 완결 편집을 포함한 어떤 경우에도 수정하지 않는다 |
| P9 | 조용하다가 반응한다 | 상태가 바뀌는 순간에만 도트, 스카이블루, 모션을 쓴다 (비주얼 문서 참조) |

## 7. Core User Loop

```
        아침 (Capture Loop)                         밤 (Read Loop)
 ┌──────────────────────────────┐          ┌──────────────────────────────┐
 │ 깨어남 → 기록(음성/텍스트)      │          │ 원고 읽기                      │
 │   → 기억 보강(≤3, 건너뛰기 가능)│  ─────▶  │   → "열린 장면" 확인            │
 │   → 처리(비동기, 떠나도 됨)     │          │   → 잠들기 전 그 장면을 떠올림   │
 │   → 새 장면 리빌 + 연결 결정    │  ◀─────  │   → (다음 날 기록 확률↑)        │
 │   → 진척 +Δ (사유 표시)         │          │                              │
 └──────────────────────────────┘          └──────────────────────────────┘
                     ↓ 완결 가능 도달
             완성하기 / 계속 꿈꾸기 → VOL.01 → VOL.02
```

**행동 메커니즘**
- 아침 트리거는 "잊기 전에"라는 손실 회피다.
- 밤 트리거는 열린 장면이 남기는 미완결 긴장이다.
- 루프가 하루의 양 끝에 걸리기 때문에, 꿈을 기억하지 못한 날에도 밤 루프 하나는 남는다.
- 밤 읽기는 꿈 인큐베이션 역할도 해서 다음 날의 공급을 늘린다.

## 9. Information Architecture

```
App
├── 원고 (Home, 기본 진입)
│   ├── 현재 볼륨 표지 (도트 커버 + 진척)
│   ├── [꿈 기록] 주 CTA
│   ├── 열린 장면 / 디렉팅 카드 (조건부)
│   └── 원고 읽기 → Reader
│         ├── 목차 (장/장면)
│         ├── 문단 탭 → 출처 시트
│         └── 편집 모드
├── 기록 (Capture, 모달)
│   └── 기억 보강 → 처리 → 리빌
├── 꿈 보관함 (Archive)
│   └── 꿈 상세 (원문 · 보강 답변 · 파생 장면)
├── 서재 (완결된 볼륨, VOL.01 완결 후 노출)
│   └── 완성본 · 내보내기
└── 설정
    ├── 알림 시간 (아침/밤)
    ├── 앱 잠금
    ├── 볼륨 설정 (각색/문체)
    └── 데이터 (내보내기 · 삭제 · AI 처리 고지)
```

- 하단 탭은 **원고 / 보관함** 2개만 둔다.
- 기록은 원고 화면의 주 CTA와 앱 아이콘 롱프레스 퀵액션으로 진입한다.
- 서재 탭은 첫 완결 이후에만 생긴다. 빈 탭을 미리 노출하지 않는다.

### 화면별 상태 규칙 (에이전트 구현용)

- **S03 원고:** 상태별로 화면이 달라진다.
  - `empty`: 볼륨 없음 → S02로 유도
  - `prologue_pending`: 첫 꿈 처리 중
  - `active`: 기본 상태
  - `completable`: 완결 제안 배너 노출
  - `completing`: 완결 처리 중
  - `completed`: 서재로 이동, 새 볼륨 유도
- **S07 리빌:**
  - 새 문단은 좌측 여백 스카이 도트로 표시하고, 첫 열람 후 잉크색으로 전환한다.
  - 연결 결정 카드는 본문 아래 1개만 둔다.
  - 진척 Δ는 최상단 메타 라인에 표시한다.
- **S08 Reader:** 스크롤 위치를 볼륨별로 저장한다. 마지막 읽은 위치에서 "이어 읽기"로 진입한다.

## 12. Dream Capture Flow

```
S03 [꿈 기록] ─▶ S04 기록 ──저장──▶ S05 기억 보강 ──완료/건너뛰기──▶ S06 처리 ─▶ S07 리빌
                  │                    (최대 3문항)
                  └─ 초안 자동저장 (앱 종료·전화 수신에도 유실 없음)
```

**S04 기록 규칙**
- 음성이 기본이다. 녹음 버튼 1탭으로 시작, 1탭으로 종료. 최대 5분.
- STT 결과는 즉시 텍스트로 표시하고 수정할 수 있다. 텍스트 모드는 토글 1개로 전환한다.
- 안내 문구는 하나만 둔다. **"장면 하나만 기억나도 괜찮아요."**
- 꿈 날짜(`dream_date`) 기본값은 오늘이다. 04시 이전 기록이면 전날 밤으로 처리한다. 수정은 상세 화면에서만 가능하다.
- 오프라인이면 로컬에 저장하고 큐에 넣는다. 연결되면 처리한다.
- 음성 원본은 STT 완료 후 **기본 삭제**한다 (§25).

**S05 기억 보강: 고정 문항 은행**

AI가 자유롭게 질문을 만들지 않는다. 자유 생성 질문은 창작 유도로 흐른다.

추출 단계에서 비어 있는 슬롯을 판별하고, 아래 은행에서 **최대 3개**를 고른다.

| 슬롯 | 질문 | 답변 형식 |
|---|---|---|
| light | 밝았나요, 어두웠나요? | 밝음 / 어두움 / 모름 |
| place | 아는 곳이었나요? | 아는 곳 / 모르는 곳 / 섞인 곳 / 모름 |
| company | 누군가 함께 있었나요? | 혼자 / 아는 사람 / 모르는 사람 / 모름 |
| self | 꿈속의 나는 어땠나요? | 나였음 / 다른 사람이었음 / 지켜보기만 함 / 모름 |
| object | 가장 기억나는 물건이 있나요? | 짧은 입력 / 모름 |
| feeling | 가장 강했던 감정은? | 불안 / 그리움 / 설렘 / 두려움 / 평온 / 모름 |
| motion | 어딘가로 이동했나요? | 이동함 / 머묾 / 모름 |
| end | 꿈은 어떻게 끝났나요? | 깨서 끊김 / 장면이 바뀜 / 모름 |
| repeat | 전에도 꾼 적 있는 꿈인가요? | 예 / 아니요 / 모름 |
| color | 기억나는 색이 있나요? | 짧은 입력 / 모름 |

- `모름`이 아닌 답변은 dream_elements에 `source=recall`로 저장한다.
- "전체 건너뛰기"를 항상 노출한다. 건너뛰어도 불이익은 없다. 진척 가산점이 없을 뿐이다.

## 13. Manuscript Generation Flow

비동기 작업 큐로 처리한다. 각 단계는 **별도 호출, 멱등, 재시도 가능**해야 서버리스 타임아웃을 피할 수 있다.

```
[E1 Extract] → [E2 Link] → [E3 Place & Plan] → [E4 Write] → [E5 Validate] → [E6 Commit] → [E7 Remember]
   경량 모델     경량+규칙      고성능 모델          고성능 모델      규칙+경량        DB 트랜잭션     경량 모델
```

| 단계 | 입력 | 출력 | 핵심 |
|---|---|---|---|
| E1 Extract | 원문, 보강 답변 | `elements[]`, `clarity`, `sensitive_flags`, 빈 슬롯 | 해석하지 않는다. 있는 것만 뽑는다 |
| E2 Link | elements, 볼륨 엔티티 레지스트리 | 엔티티 매칭 후보(신뢰도), 연결 질문 ≤1 | 신뢰도 ≥0.85는 자동 연결 후 리빌에서 표시, 0.5~0.85는 사용자 질문, <0.5는 새 엔티티 |
| E3 Place & Plan | elements, 링크, 기억(§22), 설정 | `placement`, 비트 계획(각 비트의 출처 요소 또는 C 사유) | 배치 방식 판단 |
| E4 Write | 계획, 문체, 최근 장면 2개 전문 | 문단 단위 출처 태그가 붙은 JSON | §24 규칙 |
| E5 Validate | E4 결과 | pass / fail(사유) | 실패 시 1회 재생성 → 재실패 시 **충실 모드 축약 버전**으로 폴백 |
| E6 Commit | 검증 통과 결과 | scenes, passages, progress_event | 단일 트랜잭션 |
| E7 Remember | 커밋된 장면 | story_so_far, open_threads, genre_profile 갱신 | 다음 생성의 컨텍스트 |

**배치 방식 (placement)** — 내부 판단, 사용자에게는 단순하게 노출한다.

| 내부값 | 조건 | 사용자 표시 |
|---|---|---|
| `continuation` | 기존 엔티티·장소와 강하게 연결 | "이어지는 장면" |
| `motif` | 오브젝트·감정·이미지가 반복되지만 사건 연결은 약함 | "같은 흔적이 다시 나타난 장면" |
| `interlude` | 연결이 약하고 짧은 조각 | "사이 장면" |
| `fragment_attach` | clarity=fragment, 기존 장면에 덧붙일 수 있음 | "이전 장면에 덧붙임" |
| `standalone` | 연결 불가능 | "원고 밖에 보관" (보관함에만. 나중에 넣기 가능) |

- **짧은 꿈 규칙:** clarity=fragment면 새 장면을 만들지 않는다. 문단 1~2개로 기존 장면에 덧붙이거나 사이 장면으로 넣는다 (P2).
- **첫 꿈(프롤로그):** 연결 대상이 없으므로 `prologue` 전용 프롬프트를 쓴다. 가장 공들여야 하는 생성이다. 마지막 문단은 반드시 **열린 이미지 1개**로 끝낸다. 이것이 다음 꿈의 연결 고리이자 밤 알림 문구가 된다.
- **목표 지연:** 처리 전체 p50 30초 이내, p95 90초 이내. 초과하면 "완료되면 알려드릴게요"로 전환한다.

## 14. Narrative Direction Flow

사용자 디렉팅은 세 종류뿐이다. **빈도 상한이 곧 UX 품질이다.**

| 디렉팅 | 시점 | 형식 | 빈도 상한 |
|---|---|---|---|
| D1 연결 결정 | 리빌 (S07) | "오늘의 '우산 든 여자', 2장의 그 사람일까요?" → 같은 사람 / 다른 사람 / 모르겠음 | 꿈 1개당 1문항 |
| D2 배치 변경 | 리빌 (S07) | "이어지는 장면으로 넣었어요 · 다르게 넣기" → 사이 장면 / 원고에서 빼기 | 선택 사항, 기본은 숨김 |
| D3 장르 흐름 | 원고 (S03) 카드 | 유지 / 강화(1개 선택) / 얽매이지 않기 | 장면 5개당 최대 1회 |

- **D1 결과 반영:**
  - 같은 사람 → 엔티티를 병합하고, 해당 장면을 **재작성하지 않고** 연결 문장 1개만 추가 생성한다.
  - 다른 사람 → 별도 엔티티로 등록한다.
  - 모르겠음 → `ambiguous`로 표시한다. 이후 생성에서 모호성 자체를 서사 장치로 쓸 수 있다.
- **D2 원고에서 빼기:** 해당 장면의 문단을 제거하고, 꿈은 보관함에 `archived_only`로 남긴다. 진척은 재계산하고 사유를 표시한다.
- **각색 수준 체크 (1회):** 프롤로그 리빌 하단에 "이 정도 각색이 괜찮나요?" → 좋아요 / 더 꿈에 가깝게 / 더 자유롭게. 이후에는 설정에서만 변경한다.

## 15. Progress Gauge 설계

**원칙:** 게이지는 AI 출력량이 아니라 **사용자가 공급한 재료와 결정**을 측정한다. 화면에 페이지 수를 보여주더라도, 페이지는 표시용일 뿐 계산 기준이 아니다.

### 재료 단위 (MU, Material Unit)

| 기여 | MU |
|---|---|
| 꿈 반영: clarity = fragment / partial / vivid | 1.0 / 2.0 / 3.0 |
| 보강 답변 (`모름` 제외) | 개당 +0.25, 꿈당 최대 +0.75 |
| 연결 결정 응답 (D1) | +0.5 |
| 사용자가 직접 쓴 문단 (U, 20자 이상) | +0.5, 장면당 최대 +1.0 |
| AI가 생성한 C 문단 | 0 |

- **clarity 판정 기준 (E1):**
  - 요소 수 ≤3이고 사건이 없으면 `fragment`
  - 사건 1~2개면 `partial`
  - 사건 3개 이상이거나 장면 전환이 있으면 `vivid`
  - 원문 길이는 보조 지표로만 쓴다

### 목표와 완결 조건

| 형식 | 목표 MU | 완결 가능 | 서사 게이트 (동시 충족) | 예상 도달 |
|---|---|---|---|---|
| 단편 | 20 | 14 (70%) | 장면 ≥5, 그리고 **2개 이상의 꿈에 걸쳐 반복된 엔티티·모티프 ≥1** | 평균 2.2 MU/꿈 기준 꿈 6~7개, 약 3~5주 |
| 중편 | 50 | 35 (70%) | 장면 ≥12, 반복 엔티티 ≥3, 열린 스레드 ≥2 | 꿈 15~18개, 약 2~3개월 |

- `progress = min(1, Σ MU / target_MU)`
- **완결 가능**은 수치 조건과 서사 게이트를 모두 충족할 때만 뜬다. 서사 게이트는 엔딩이 회수할 재료가 있는지 보장한다.
- 100%를 넘으면 게이지는 100%로 고정하고 "완결 가능 · 계속 쌓는 중"을 표시한다.

### 표시 형식

```
VOL.01                                   42%
7 dreams   11 scenes   약 35p

오늘  새 장면 1   연결 1 확정   +6%
```

- `약 Np`는 원고 총 글자 수 ÷ 700이다 (국문 단행본 1쪽 기준). 표시 전용이다.
- **Δ 사유 문구 템플릿:** 새 장면 {n} / 덧붙인 조각 {n} / 연결 {n} 확정 / 직접 쓴 문장 {n} / 기억 보강 {n}
- **감소는 사용자가 뺀 경우에만 한다.** 그 경우 "3월 4일 꿈을 원고에서 뺐어요 −8%"로 표시한다.

## 16. 단편 / 중편 Completion 구조

### 완결 제안 (S14a)
"이 이야기는 이제 완결할 수 있습니다." → **여기서 완성하기** / 계속 꿈꾸기 / (단편일 때) 중편으로 늘리기
- "계속 꿈꾸기"를 고르면 이후 목표 MU의 +20%마다 1회씩 다시 제안한다. 과도하게 반복하지 않는다.

### 완결 파이프라인

| 단계 | 처리 | 사용자 터치포인트 |
|---|---|---|
| C1 구성 | 장면 요약 목록 → 장(chapter) 묶음 제안 (단편 3~4장, 중편 6~10장), 재배치·병합 제안 | **S14b 구성 확인:** 제안 수락 / 기록 순서 그대로 |
| C2 연결 개정 | 장 단위로 C 문단 재작성. 전이와 복선 정리 | 없음 |
| C3 문체 통일 | D 문단은 **어휘·문장 부호 수준만** 통일 (diff 보존). U 문단 불가침 | 없음 (결과는 되돌리기 가능) |
| C4 엔딩 | 열린 스레드와 반복 모티프로만 엔딩 방향 2개 제안 → 선택 후 생성 (C 태그) | **S14c:** 엔딩 방향 A / B |
| C5 제목 | 제목 후보 3개 + 직접 입력 | **S14d:** 제목 선택, **작가의 말 작성** (AI 초안 없음, 건너뛰기 가능) |
| C6 조판 | 표지 (§비주얼), 차례, 본문, 작가의 말, 부록 "이 책의 꿈들" | **S14e:** 표지 리빌 → 완성본 |

**잠금 정책 (P8)**

| 출처 | 완결 편집 허용 범위 |
|---|---|
| U (사용자) | 수정 불가 |
| D (꿈) | 어휘·문장 부호 통일만. 의미 변경 금지. 원문 diff 보존 |
| C (연결·각색) | 재작성 가능 |
| 엔딩 | 새로 생성하되 C 태그를 붙이고 출처 시트에 "완결 시 작성된 엔딩" 표시 |

- 완성 후 **"완결 편집 되돌리기"**로 C2~C4 이전 상태를 복구할 수 있다. 완성 후 7일까지.
- 산출물: 앱 내 완성본과 PDF. ePub은 MVP 이후.

## 17. 문체 / 각색 수준 설정 구조

S02에서 선택한다. 둘 다 **기본값이 선택된 상태**로 제공하고, 설정에서 언제든 바꿀 수 있다. 변경은 이후 생성부터 적용되고, 완결 시 C3에서 통일된다.

**각색 수준 → 엔진 파라미터**

| 수준 | 사용자 설명 | C 예산 (글자 기준) | 새 엔티티 | 새 사건 | 길이 상한 배수 |
|---|---|---|---|---|---|
| 꿈에 충실하게 | 꿈에 나온 것 중심, 최소한의 연결만 | ≤15% | 금지 | 금지 (전이 동작만) | ×1.0 |
| **균형 있게 (기본)** | 꿈 중심 + 자연스러운 서사 보강 | ≤35% | 이름 없는 단역만 | 소규모 허용 | ×1.3 |
| 자유롭게 | 꿈을 소재로 적극 확장 | ≤60% | 허용 (C 태그 필수) | 허용 | ×1.6 |

**문체 → 스타일 가이드 프롬프트**

| 문체 | 규칙 요약 |
|---|---|
| **담백하게 (기본)** | 짧은 평서문, 수식어 최소, 감정은 행동으로 표현, 비유는 장면당 1개 이하 |
| 서정적으로 | 감각 묘사 비중을 높임, 문장 호흡을 길게, 반복과 리듬 허용 |
| 영화적으로 | 컷 단위 전환, 현재형 비중을 높임, 시각·음향 디테일, 대사는 짧게 |

**길이 상한 (P2):** 기본 상한은 clarity별로 fragment 300~700자, partial 800~1,800자, vivid 1,500~3,500자이고, 여기에 각색 배수를 곱한다.

## 18. Genre 동적 형성 로직

- **분류 체계 (고정 8개):** 미스터리, 초현실, 드라마, 호러, 로맨스, 판타지, 성장, 블랙코미디
- **장면별 점수:** E7에서 장면마다 8개 장르에 0~1 점수를 매긴다.
- **볼륨 프로필:** 지수이동평균 `profile = 0.7 × profile + 0.3 × scene_scores`
- **카드 노출 조건:**
  - 장면이 4개 이상이면서 상위 2개가 최근 2회 연속 동일하거나, 1위 장르가 바뀌었을 때
  - 그리고 장면 5개당 최대 1회
- **카드 문구:** "지금 이 이야기에는 미스터리와 초현실의 성격이 나타나고 있어요."
- **선택 → `genre_directive`**
  - 유지: `{mode:"keep"}`, 기본 동작과 같다
  - 강화: `{mode:"amplify", target:"미스터리"}`
  - 얽매이지 않기: `{mode:"free"}`, 장르 편향 제거
- **강화의 효과는 각색 수준을 넘을 수 없다.**
  - 충실: 어조, 어휘, 속도만 조정
  - 균형: 위에 더해 소규모 사건
  - 자유: 위에 더해 플롯 장치
- **원고 화면 표시:** 장르는 태그로만 보여준다 ("미스터리 · 초현실 성향"). 잠금이 아니며 이후 꿈에 따라 계속 바뀐다.

## 19. Source of Story UX

- **출처 시트 (문단 탭):**
  - 출처 배지: 꿈에서 / 연결 / 내가 씀
  - 날짜: "3월 4일 기록한 꿈"
  - 원문 발췌: 해당 요소를 강조
  - 원문 전체 보기
  - C 문단일 때는 연결 사유 1줄: "2장의 붉은 문과 오늘의 문을 잇는 문장"
- **여백 출처 표시 (Reader 토글, 기본 OFF):** 좌측 여백에 D = 채운 점, C = 빈 원, U = 짧은 세로선. 도트 언어를 출처 표기로 쓰는 것이다 (비주얼 문서 참조).
- **볼륨 출처 비율:** 완성본 판권면에 "이 책의 문장 중 68%는 당신의 꿈에서, 5%는 당신의 손에서 왔습니다" (글자 수 기준, D와 U 비율).
- **부록 "이 책의 꿈들":** 볼륨에 반영된 꿈의 날짜와 첫 줄 목록. PDF에 포함한다. 원문 전체는 포함하지 않는다 (공유 시 프라이버시).

## 20. Dream Archive 구조

- **목록:** 월별로 묶는다. 항목마다 날짜, 원문 첫 줄, clarity 점(1~3개), 상태.
- **상태값:** `processing` / `in_manuscript` / `archived_only` / `failed`
- **필터:** 전체 / 원고에 반영 / 기록만
- **꿈 상세 (S13):** 원문(수정 가능), 보강 답변, 파생 장면 링크, 행동(원고에 넣기 또는 빼기, 삭제)
- **원문 수정 시:** 이미 생성된 장면은 자동으로 재생성하지 않는다. "이 꿈에서 온 장면 다시 쓰기"를 선택 사항으로 제공한다.
- **삭제 시 선택:**
  - (a) 파생 D 문단도 삭제
  - (b) 문단은 남기되 출처 연결 해제 → C로 강등
  - 기본은 (a)
- **`archived_only` 꿈 → "원고에 넣기":** E3부터 재실행한다. 현재 원고 끝에 배치한다.

## 21. AI Narrative Engine의 핵심 역할

엔진의 일은 **6개뿐이다.** 이 목록 밖의 일은 하지 않는다.

1. **Extract:** 꿈에서 있는 것만 구조화한다.
2. **Link:** 기존 엔티티·모티프와 동일성을 판단하고, 애매하면 사용자에게 묻는다.
3. **Place:** 원고 안의 위치와 배치 방식을 정한다.
4. **Write:** 허용된 각색 범위 안에서 출처 태그가 붙은 문단을 쓴다.
5. **Remember:** 다음 생성을 위한 서사 기억을 갱신한다.
6. **Compile:** 완결 시 구성, 연결, 엔딩을 편집한다.

**하지 않는 것:** 해몽과 심리 해석, 꿈의 의미 설명, 태그 없는 창작, U 문단 수정, 사용자에게 창작 질문하기.

## 22. Narrative Memory / Context 설계 개요

**컨텍스트 레이어 (E3·E4 호출 기준, 토큰은 대략치)**

| 레이어 | 내용 | 예산 | 캐싱 |
|---|---|---|---|
| L0 시스템 | 엔진 규칙, 출처 태깅 스키마, 금지 규칙 | ~1.5k | 프롬프트 캐시 |
| L1 설정 | 각색 수준, 문체 가이드, genre_directive, 시점(POV) | ~0.5k | 캐시 |
| L2 볼륨 바이블 | 엔티티 레지스트리(역할명·한 줄 설명·등장 장면), 세계 규칙, 반복 모티프 | ≤2k | 볼륨 버전별 캐시 |
| L3 서사 요약 | story_so_far (롤링 요약), open_threads (≤5) | ≤1.5k | 커밋마다 갱신 |
| L4 최근 원문 | 직전 장면 2개 전문 | ≤3k | — |
| L5 오늘 | 원문, elements, 보강 답변, D1 결정 | ≤1.5k | — |

- 총 입력 약 10k 토큰 이내로 유지한다. 원고가 길어져도 L2와 L3는 요약·압축으로 상한을 지킨다. **원고 전문을 넣지 않는다.**
- **엔티티 레지스트리 압축 규칙:** 등장 횟수와 최근성으로 상위 20개만 L2에 넣는다. 나머지는 이름과 1단어 설명만.
- **Remember 갱신 (E7):**
  - story_so_far를 재작성한다. 증분 요약이고 1.5k 상한.
  - open_threads는 추가, 해소, 유지를 판정한다.
  - 엔티티 설명을 갱신한다. 새 속성만 추가하고 기존 속성은 유지한다.
- **비용 (추정):** 꿈 1건 처리에 약 50~150원. 단편 완결 1회에 약 500~1,500원. 비용은 병목이 아니므로 **품질을 우선**한다.

## 24. AI 생성 시 지켜야 할 핵심 규칙

### 생성 규칙 (L0 시스템 프롬프트에 명시)

1. 모든 문단은 `origin`을 가진다. D 문단은 `source_element_ids`가 1개 이상이어야 한다.
2. salience=high인 요소는 반드시 1회 이상 사용한다. 꿈의 핵심을 버리지 않는다.
3. 각색 수준의 C 예산, 새 엔티티 규칙, 길이 상한을 넘지 않는다.
4. 등장인물은 **역할명**으로 부른다 ("우산 든 여자"). 원문에 실명이 있어도 원고에는 역할명을 쓴다.
5. 꿈을 해석하거나 의미를 설명하지 않는다. 교훈과 요약으로 맺지 않는다.
6. **메타 꿈 표현 금지:** "꿈에서 깨어났다", "마치 꿈처럼", "그것은 꿈이었다", "눈을 떠보니". 꿈을 꿈이라 부르지 않고 **현실처럼 쓴다.**
7. 장면을 닫지 않는다. 마지막 문단은 열린 이미지나 미해결 요소로 끝낸다 (엔딩 제외).
8. U 문단(locked)은 입력으로만 참조하고 출력에 포함하거나 수정하지 않는다.
9. 성적으로 노골적인 묘사는 암시와 생략으로 처리한다. 미성년자가 관련된 성적 내용은 생성을 거부한다 (§25).
10. 출력은 스키마를 따르는 JSON만 낸다.

```json
    { "origin": "C", "c_reason": "2장의 복도와 오늘의 계단을 잇는 전이", "text": "..." }

```

### E5 검증기 (규칙 기반 우선, 경량 모델은 V5와 V7에만)

| ID | 검사 | 실패 시 |
|---|---|---|
| V1 | JSON 스키마 유효 | 재생성 |
| V2 | C 비율(글자) ≤ 예산 | 재생성 (C 축소 지시) |
| V3 | 새 이름 엔티티 ⊆ (오늘 elements ∪ 레지스트리). 자유 모드는 C 태그면 허용 | 재생성 |
| V4 | 총 길이 ≤ 상한 | 초과분 절단 불가 → 재생성 |
| V5 | high salience 요소 누락 없음 | 재생성 |
| V6 | locked 문단 해시 불변 | **즉시 폐기** (버그로 취급) |
| V7 | 금지 표현(규칙 6), 실명 노출, 안전 기준 | 해당 문단만 재생성 |

**2회 실패 시 폴백:** 충실 모드, 연결 문장 0~1개, 원문 요소를 순서대로 서술하는 축약 장면을 만든다. 품질은 낮아도 원칙은 지킨다.

## 25. Privacy / 민감한 꿈 데이터 처리 원칙

- **등급:** 꿈 원문은 법적 민감정보가 아니더라도 **민감정보와 같은 등급으로 취급**한다. 성, 고인, 가족 갈등, 트라우마가 수시로 섞여 들어오기 때문이다.
- **AI 처리 고지:** 온보딩과 설정에 "꿈 내용은 원고 생성을 위해 AI 모델 제공사로 전송됩니다"를 명시한다. 모델 학습 사용 여부와 보존 기간은 **채택한 제공사의 API 약관을 확인한 뒤** 사실대로 기재한다.
- **저장:**
  - Supabase RLS로 사용자별 격리. 저장 시 암호화는 매니지드 기본값을 쓴다.
  - 앱 잠금은 Face ID와 패스코드. 기본은 OFF이고 온보딩에서 제안한다.
- **음성:** STT 완료 후 원본 음성을 삭제하는 것이 기본값이다.
- **로그:** **분석 이벤트, 서버 로그, 에러 리포트에 꿈 텍스트와 생성 문장을 절대 넣지 않는다.** 이벤트에는 ID와 메타데이터만 넣는다. 가장 흔한 사고 경로다.
- **삭제:**
  - 꿈 삭제는 §20의 선택지를 따른다.
  - 계정 삭제 시 즉시 하드 삭제한다. 백업 잔존 기간은 고지한다.
  - 전체 데이터는 JSON이나 텍스트로 내보낼 수 있다.
- **실존 인물:** 원고의 기본은 역할명이다. 실명은 사용자가 편집에서 직접 쓸 때만 들어간다. 이는 향후 공개 기능의 명예훼손과 개인정보 리스크를 미리 차단한다.
- **민감 콘텐츠:** 기록은 모두 허용한다. 생성은 §24 규칙 9를 따른다.
- **연령:** **만 14세 미만은 가입할 수 없다** (법정대리인 동의 절차를 MVP에서 다루지 않기 위해). 앱 연령 등급도 이에 맞춘다.
- **위기 신호:** 죽음이나 폭력이 나오는 꿈은 흔하므로 꿈 내용만으로는 개입하지 않는다. **깨어 있는 현실에서의 자해 의도 표현**이 감지될 때만 생성과 별개로 도움 안내 카드를 1회 보여준다. 과잉 감지는 금지한다.

## 30. Novelty Toy vs 애착 있는 창작 도구 판단 기준

표본이 수백 명 수준이라 **정량 신호와 완성자 전원 인터뷰를 병행**한다. 아래 수치는 초기 휴리스틱이다.

| 신호 | Toy | Tool |
|---|---|---|
| A2 두 번째 꿈 (14일) | < 30% | ≥ 45% |
| 꿈당 체류 시간 추이 | 회차마다 감소 | 유지 또는 증가 |
| 무알림 원고 오픈 | 리텐션 사용자 기준 거의 0 | 주 1회 이상 |
| 편집 | 거의 없거나 삭제·되돌리기 위주 | **새 문장 추가형** 편집이 존재하고 작가 비율이 상승 |
| 완결 가능 도달 (30일) | < 5% | ≥ 15% |
| 완성률 (completable 중) | < 30% | ≥ 50% |
| 작가의 말 작성률 | < 20% | ≥ 50% |
| **VOL.02 시작률** | < 15% | ≥ 40% |
| 인쇄본 대기 신청 | 거의 0 | 완성자의 20% 이상 |

**판정:**
- 아래 네 개가 모두 Tool이면 계속한다: A2, 무알림 오픈, 완성률, VOL.02.
- **A2는 Tool인데 무알림 오픈이 Toy면**, 사람들은 이 앱을 꿈 일기로 쓰고 있고 소설은 장식이다. 이 경우 "기록 → 월말 한 편" 같은 가벼운 구조로 피벗하는 것을 검토한다.
- **A1은 높은데 A2가 Toy면**, 첫 경험은 신기함에 그친 것이다. 프롤로그 품질과 밤 루프부터 재검토한다.

## 32. 남아 있는 구조적 충돌 (지적)

1. **"자유롭게" 모드 vs Source of Story.** 제품의 차별점은 출처다. 그런데 자유 모드는 출처를 희석하는 기능이다. 동시에 가지려면 출처 비율을 항상 드러내야 하고, 그러면 자유 모드 사용자는 낮은 D 비율을 보게 된다. 둘 중 하나가 불편해진다. → 31-1
2. **시작 화면의 3가지 선택 vs "결정은 알맞은 때에".** 길이, 각색, 문체를 아무것도 모르는 첫 화면에서 고르게 한다. 원칙 P3·P4와 같은 계열의 충돌이다. → 기본값 선택 + 길이 제거(31-2) + 프롤로그 후 각색 체크로 완화했다.
3. **완결 시 AI 전체 편집 vs Author.** "AI가 구조, 문체, 엔딩을 편집해 완성한다"와 "사용자가 작가가 된다"는 충돌한다. → U 잠금, D 통일 범위 제한, 사용자 터치포인트 4개(구성, 엔딩, 제목, 작가의 말), 완결 되돌리기로 해소했다. 그래도 작가의 말을 건너뛴 완성본은 오너십이 약하다.
4. **설치 시점 vs 루프 시작 시점.** 설치는 대부분 낮에 일어나고, 루프는 기상 직후에 시작된다. → Day 0에 과거 꿈을 허용해 해소했다. 이게 없으면 첫날 이탈이 구조적으로 발생한다.
